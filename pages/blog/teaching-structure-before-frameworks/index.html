Teaching Structure Before Frameworks

How a simple HTML, CSS, and JavaScript project template became a way to teach separation of concerns, collaboration, deployment, and the reasoning behind software structure before students encountered larger frameworks.

Context

Used in

Later reused in

Core Principle

August 11, 2026

01 / Why I Needed a Standard

Before Architecture, There Was the Root Folder

Students were learning HTML, CSS, and JavaScript, but many entered with weak project-organization habits. Everything could land in the root directory: long image names, giant files, presentation and behavior mixed into HTML, and no clear owner for an asset.

The consequences appeared as projects grew. Navigation and checking became harder, maintenance slowed, structures differed between students, and collaborative work produced avoidable overlap and merge conflicts. The goal had to be larger than syntax. I wanted the class to share a development standard and a language for where files belonged, which part owned a responsibility, how work could be divided, and how another developer could understand and deploy the site.

A working page was not enough if nobody could understand where its parts belonged.

02 / The Template Was Deliberately Empty

The Scaffold Was the Lesson

AWD-WD-Template-Project standardized the boundaries without supplying a finished website.

The public scaffold required `WD-` project naming, `index.html`, descriptive page folders, camelCase files, external CSS, files in their respective directories, README prompts, and a GitHub-oriented workflow. The empty starter files were intentional: students still had to design and build the site. The standard gave them constraints without giving them the answer.

03 / Separation of Concerns First

HTML Was Not Allowed to Become Everything

As a classroom standard, I was strict: no inline CSS, no internal CSS, no inline or internal JavaScript, and files had to be placed according to purpose.

HTMLStructure and content
CSSPresentation
JavaScriptBehavior
AssetsSupporting resources
PagesIndependently understandable site areas

Students could technically make a website work with everything inside one file. That was not the habit I wanted to normalize. External files are not universally required for every possible website; this was a teaching constraint designed to make responsibility visible early.

Separation of concerns becomes much harder to learn after bad habits already feel normal.

04 / Why index.html Kept Appearing

A Small Convention Preparing Them for Larger Systems

Each page directory kept its own `index.html`. That made the structure predictable, supported clean static-page organization and GitHub Pages deployment, and introduced route-oriented thinking without pretending to be a framework.

The larger lesson was that a file's name and location can participate in how a system works. Frameworks and platforms later bring their own conventions: directories carry meaning, routes map to files or modules, and expected filenames own specific responsibilities. They do not all use this folder tree. The scaffold simply prepared students for the idea that structure can be operational.

05 / The First Question Was: What Technology Owns This?

How I Taught Them to Decide Where Files Belong

What is it?→Which technology owns it?→What concern is it?→Page-specific or shared?→Smallest sensible boundary

I asked what technology was responsible for the information, which language or file type expressed it, what logic or concern it represented, whether it belonged to one page or many, and who or what consumed it. The folder came after the responsibility.

The important thing is not the folder name. It is understanding why the file belongs there.

06 / Structure Made Team Work Possible

A Folder Could Also Become an Ownership Boundary

Once the class understood the same structure, students could move from individual pages into collaborative projects with clearer places to work.

Developer 1

  • Landing page
  • Page CSS and JavaScript
  • Page-owned images

Developer 2

  • Another page or feature
  • Its local assets
  • Defined responsibility

Developer 3

  • Another page or feature
  • Shared changes coordinated
  • Known ownership boundary

Students knew where their page, CSS, JavaScript, and images belonged, and which shared files should not be changed casually. I observed fewer merge conflicts, clearer ownership, easier coordination, and easier checking. Structure did not eliminate collaboration problems; it gave the team clearer places to work.

07 / When Everything Lives in One File

The Cost Appeared When Projects Became Larger

Before · root accumulation

Root
├── index.html
├── randomImageReallyLongName.jpg
├── anotherImage.png
├── script.js
├── styles.css
├── page2.html
├── page3.html
└── ...

After · deliberate boundaries

Intentional directories↓Smaller responsibilities↓Predictable locations↓Easier collaboration↓Easier maintenance

The primary cost was development and maintenance complexity: difficult navigation, slower understanding, unclear ownership, repeated code, conflict-heavy collaboration, and unwieldy files. I did not teach that folder organization by itself made a deployed site run significantly faster.

08 / Public Code Changed the Expectation

If It Was Deployable, It Had to Be Understandable

Student work was expected to live in a public GitHub repository and be deployable through GitHub Pages. Someone besides the author could encounter the code, so naming, structure, README content, maintainability, and presentation became visible responsibilities.

The question became: who might continue this project, and could they understand it? This connected to my Git/GitHub teaching, but the emphasis here was different. The Git retrospective covers collaboration, history, branching, and recovery. This lesson focused on structure and ownership.

09 / Then They Met Frameworks

The Folders Changed. The Principle Did Not.

The same template later served as a starter or reference for some CodeIgniter 4 students who had not taken my Web Design or Advanced Web Design classes. Students already familiar with separating files appeared less confused by larger structures and less prone to basic organization mistakes. I observed easier onboarding and project startup, not a measured causal result.

Static web structure→Responsibilities→MVC→N-Layer→Feature-based and other architectures

The template did not become MVC, N-Layer, or feature-based architecture. Different architectures organize boundaries differently. It introduced the underlying idea that responsibilities deserve deliberate boundaries, while students still had to learn both the current required structure and the reason it existed.

The folders changed when the technology changed. The reason for separating responsibilities stayed.

10 / Following Without Understanding

A Standard Can Become Another Bad Habit

Some students over-applied the pattern and created unnecessary directories or separations because they were following it mechanically. That became another teaching opportunity. The lesson was never that more folders were better.

The mature rule was to follow the structure required by the current technology and project while understanding the responsibility being separated. Blind conformity could become as unhelpful as no structure at all.

Technology↓Language or representation↓Logic or concern↓Shared or local responsibility↓Structure

11 / What Changed

They Could Start Bigger Projects Faster

Observed outcomes, not measured KPIs

  • Cleaner repositories
  • Fewer merge conflicts
  • Better collaborative work
  • Easier checking
  • Faster project initialization
  • Better coordination
  • Greater familiarity with larger structures
  • Fewer basic structural mistakes around frameworks
  • Better awareness of maintainability
  • More consideration for whoever continued the codebase

Repeated use made the shared structure familiar enough that students appeared able to begin larger projects sooner and coordinate responsibilities earlier. I am not assigning percentages or exact time savings to that observation.

Students I later encountered in CodeIgniter 4 and more structured applications appeared less prone to basic project-organization mistakes and seemed to understand new structures faster. That is a classroom observation, not measured causation.

12 / Closing

The Template Was Never the Point

What I am proudest of is the deployed work students produced using these standards. The underlying practices also stayed with me.

Establish responsibilities→Separate concerns→Make locations predictable→Organize for whoever continues the work

I still use those principles in my own projects, including this portfolio. That does not mean this site uses the exact AWD-WD folder tree. The connection is the practice of making responsibility and continuation deliberate.

The template was temporary. The reasoning survived it.

The important thing is not the folder name. It is understanding why the file belongs there.
