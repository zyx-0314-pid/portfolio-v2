Why Game Balance Is Harder Than It Looks

In 2023, during my fourth year in college, I built a small turn-based game in PyGame to experiment with combat math. Writing attacks, potions, critical hits, and character stats was manageable. Making all of those numbers feel fair together was the harder problem.

01 / Starting Small

I Wasn't Trying to Build a Huge Game

I built the game in 2023, during my fourth year in college, as a class-related learning experiment. A relatively simple turn-based format gave me room to focus on rules and numbers rather than real-time movement or a large world. Character selection, combat statistics, potions, and changing state were already enough to study.

I liked the ideas of a Samurai and an Archer, so I used them as two playable configurations. That was personal preference, not a sophisticated product decision. The visual assets came from free online sources; I do not claim ownership of them. I primarily wrote the programming, combat rules, stat systems, and game logic independently, with an implementation that differed from tutorial examples I encountered at the time.

02 / What Was Actually Being Calculated

A Battle Was Really a Set of Numbers

  • HP
  • Strength
  • Accuracy
  • Critical Chance
  • Critical Damage
  • Healing
  • Temporary Stat Boosts
  • Effect Duration
  • Potion Quantity
  • Enemy Statistics

Normal damage ≈ Strength

Critical damage ≈ Strength × Critical Damage Multiplier

The code uses probability checks for accuracy and critical hits. I selected the values manually rather than generating them from a formal balancing model.

04 / Then I Added Potions

Every New Variable Made Balance Harder

The experiment expanded from basic attacks into healing, strength, accuracy, critical chance, critical damage, duration, and inventory quantity.

Use item↓Apply effect↓Modify character state↓Remain active for N turns↓Expire↓Remove temporary change

The code stores active effects, decreases their remaining turns, and removes temporary changes when they expire. Balancing one stat in isolation was easy. Balancing it while potions and skills could temporarily modify that stat was much harder.

05 / The Real Development Loop

My Balancing Algorithm Was Basically: Play It Again

Choose numbers↓Play battle↓Something feels wrong↓Adjust stats↓Play again
Writing the combat system was easier than balancing it.

Too much damage ended fights quickly. Too much HP made them drag. One character could become obviously stronger, potions could dominate a battle, and critical hits could make an outcome feel excessively random.

Changing one value affected several relationships. Enemy difficulty could jump too quickly or become trivial. There was no advanced optimization model behind the process: I chose numbers, played, adjusted them, and repeated.

06 / Randomness Complicated Everything

Randomness Made the Same Numbers Behave Differently

The implementation randomly selects an enemy and uses random checks for attack accuracy and critical hits. Identical character statistics therefore do not guarantee identical encounters.

Player statsEnemy statsPotions and buffsRandom accuracyRandom critical hits
↓Actual battle outcome

I especially enjoyed this part because randomness made the game less deterministic and the balancing problem more interesting. A configuration that felt right in one playthrough could feel different in another. I responded with repeated manual playtesting, not statistical simulation.

08 / The Part That Consumed the Project

Game Balance Consumed More Time Than I Expected

The game stayed small partly because college-project time was limited and balancing the existing combat already required substantial experimentation. Maps, quests, larger progression systems, saving, and similar additions were not the priority.

This was not a carefully planned minimum viable product strategy. The existing battle system simply produced enough interacting variables to study. Even within that narrow scope, each added statistic or temporary effect created more relationships to reconsider.

09 / Looking at the Code Years Later

The Old Code Is Part of the Point

Retrospective observations, not a modern architecture review

Visible student-era choices

  • Manually defined configuration values
  • Repeated potion definitions
  • String-based effect identifiers
  • A large procedural battle loop
  • UI and game state coupled in places

Ideas that still stand out

  • Shared character behavior
  • Separate Player and Enemy behavior
  • Reusable UI and button components
  • Scene separation
  • Temporary state handling
  • Interacting combat variables
It does not need to look like code I would write today to remain useful evidence of what I was learning then.

I would structure several systems differently now. That does not erase the useful decisions already visible in the experiment or justify rewriting its history with modern terminology.

10 / Why I Understand Balance Patches Better Now

One Number Rarely Changes Only One Thing

A +5 change is not just +5. Its effect depends on everything that interacts with it.

Damage + cooldown + scaling

Health + item effectiveness + recovery

Critical probability + attack frequency + critical severity

Games such as League of Legends make this relationship familiar to players. When a competitive game changes damage, cooldown, health, item effectiveness, critical probability, resources, or scaling, the impact cannot be understood by reading that number alone. I am not claiming to know the developer's exact balancing process. The college experiment simply gave me a practical reason to appreciate why apparently small patches can change many relationships.

11 / What Stayed With Me

Balance Is a System Problem

I started the project because I wanted to experiment with game development and numbers. The code taught me how attacks, state, probability, and temporary effects could work.

The repeated playtesting taught me something more useful: a system can be individually understandable and still become difficult to balance once its parts interact.

The game was small.
The balancing problem wasn't.
