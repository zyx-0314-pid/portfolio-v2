Teaching Git Before It Was in the Syllabus

How a Git/GitHub reference I built for my students became part of how they learned teamwork, recovery, and software-development workflow.

Context
FEU Institute of Technology
Used in
Web Design · Advanced Web Design · PHP · Android · C++ · HCI
Reach
Approximately 50 students per class
Source
Github-Git-Guide ↗

01 / Why I Built It

A Reference That Did Not End With the Lecture

Git and GitHub were not part of the formal syllabus, but I made them required in my classes because the students' projects already depended on teamwork, shared code, and repeatable setup.

A live demonstration could show the workflow once. It could not guarantee that every class received the same explanation, or help a student who needed to repeat a step later without me present. The guide became the durable part of the lesson.

It was never finished in one pass. Questions from actual classes exposed missing setup steps, unclear assumptions, and recovery cases. I revised the repository around those questions so the next student could find the answer directly.

02 / Mental Model

GitHub Is Not Google Drive

Students often approached GitHub like Google Drive: put the project online and keep the latest copy there.

Google Drive mindset

Project→Upload→Latest file

Git workflow

Working code↓Commit↓Version history↓Branch↓Push↓Pull request↓Review↓Main
Git does not merely store the project. It records how the project changes.

That distinction changed the meaning of a mistake. A broken edit was no longer automatically catastrophic; with useful history, it became something the team could inspect and recover from.

03 / Collaboration

A Branch Became a Boundary of Responsibility

A branch is not just a copy of the code; it is a boundary of responsibility.
Branch→Commit→Push→Pull request→Review→Merge

Once each change had a branch and a review path, roles were easier to explain as ownership of a specific kind of work rather than titles assigned to a group.

RoleResponsibility
Frontend DeveloperViews and frontend implementation
Backend DeveloperControllers, services, behavior, and repositories
DB AdministratorMigrations, schema, seeding, and DTOs
TesterVerify changes before merge
Project LeaderReview and merge pull requests

04 / Structure

Why Naming Started to Matter

At first, students created branches and commits with random names. The cost appeared when nobody could quickly determine what a teammate was working on, pull requests mixed unrelated work, and ownership was unclear.

Those names also became part of later debugging. A history full of vague messages could not explain when behavior changed or which decision introduced it.

Feature-based work→Structured branches→Meaningful commits→Testing→Pull request→Merge

The guide's branching and Conventional Commit guidance grew from that operational need: names had to communicate intent before a reviewer opened the code.

05 / Documentation

README Wasn't Decoration

The real test was simple: could another person reproduce this project without borrowing the developer's computer?

This mattered when students moved between computers, when another group member joined the work, and when I needed to check a repository on my own machine.

It also introduced a professional expectation: future developers should be able to understand the setup without relying on memory or private instructions.

06 / Recovery

Three Times Git Paid for Itself

01

The Exhausted Rewrite

A student was exhausted while revising a module and accidentally removed a large amount of code, affecting adjacent functionality. The following day, version history allowed the work to be recovered rather than reconstructed manually.

Commits are recovery points.

02

The Test State

A student committed a test state before going to school because she wanted to preserve what she had. The team retained history showing what changed and where they could return instead of treating the change as irreversible.

History provides options.

03

Five Minutes Before a Capstone Presentation

The latest main branch had an issue during a thesis or capstone presentation. Debugging under presentation pressure was the wrong task, so the team returned main to the previous working state and let the deployment workflow run again.

Broken latest main↓Previous working state↓CI/CD runs again↓Stable version deployed↓Presentation recovered
Version control became operational risk control. Recovery took approximately five minutes.

07 / What Changed

The Classroom Became Easier to Operate

Observed outcomes, not measured KPIs

  • Better Git habits
  • Faster repeated environment and setup work
  • Fewer repeated Git questions
  • Easier group collaboration
  • More explicit responsibilities
  • More confidence recovering mistakes
  • A reusable reference beyond lectures and laboratories

The repository's troubleshooting material expanded around real setup problems: missing clone actions, Git installation, pulling between devices, and unexpected VS Code behavior. Each addition reduced the need to solve the same issue privately again.

08 / Beyond My Class

What They Carried With Them

Students carried the workflow into OJT, thesis and capstone work, personal projects, and eventually their jobs. Some asked permission to continue using the guide even though it was already public. Students I had never personally taught also knew the repository.

I do not know the exact origin of the name “Huling Lahi” or “Huling Lahi ni Sir Ian,” but it eventually reached me as a nickname associated with students who had gone through my classes and carried those practices with them.

The meaningful part was not that they remembered a repository. It was that the habits remained useful after the class that introduced them.

09 / Closing

The Tool Was Never the Important Part

Git was the tool.

Work can be divided.
Changes can be reviewed.
Mistakes can be reversed.
Another person should be able to understand what happened.
