Teaching Reproducibility Before Deployment

How Docker, migrations, environment configuration, and database discipline helped students move from machine-dependent PHP projects to development environments they could recreate, collaborate on, and prepare for deployment.

Context
FEU Institute of Technology
Used in

Preparation

Environment

01 / The Problem

The Project Worked - On One Computer

Students could write working PHP applications while the development setup itself remained fragile. Databases were configured manually, schema changes existed on one machine, ports and software versions differed, and moving between home and school could mean rebuilding undocumented setup.

This was bigger than PHP syntax. Collaboration became difficult when a teammate could pull the code but could not reproduce its configuration or database state. These were classroom observations, not a measured industry study.

If the project only works on the computer where it was built, the environment has become an undocumented dependency.

02 / Why I Moved Away from XAMPP

I Wanted the Environment to Travel With the Project

XAMPP can be useful. My teaching reason for preferring Docker was that students could describe a shared environment instead of configuring each local stack independently.

Repository↓Docker configuration↓Application and services↓Consistent base environment

The goal was to reduce manual database setup, operating-system and version differences, collaboration friction, environment drift, and local changes teammates could not reproduce. Windows, Linux, and macOS still have host differences and must support the required Docker environment, but the project definition no longer needed three unrelated versions.

The goal was not Docker for Docker's sake. The goal was one reproducible setup.

03 / One Setup for the Team

Clone, Configure, Start, Continue

Clone or pull repository→Create local .env→Start Docker environment→Apply migrations→Seed required data→Continue development

The public template documents docker compose up --build and docker compose watch, exposes configurable ports, includes a sample environment file, and defines shared PHP, MongoDB, and PostgreSQL services. The class workflow also treated migrations and seeders as part of reconstructing database state, although those files are not present in the current public template snapshot.

Everyone shared the same base definition while retaining local configuration. The real `.env` stayed uncommitted; the repository documented which values another developer needed to provide.

04 / I Made Them Change Computers

Reproducibility Was Not Theoretical

At home, students naturally used their own machines. In school, I intentionally required them to use available school computers rather than relying on personal devices. I wanted the project to prove that it could move.

HomeCode↓Commit and push
→
SchoolClone or pull↓Configure environment↓Start services↓Apply database state↓Continue coding
→
Home againPull↓Continue

I observed students switching devices with much less setup-specific friction after repeated practice. Some became comfortable enough to continue from another suitable computer, including a computer shop when the machine could run the required Docker environment. That anecdote demonstrates portability of the workflow, not that every public computer is appropriate for development.

The machine changed. The project did not have to.

05 / The Database Had to Travel Too

Code Was Versioned. The Database Needed a History Too.

Application change↓Database requirement changes↓Migration↓Team applies migration↓Same expected schema
Known development or test state↓Seeder↓Repeatable starting data

A teammate should not need an instruction such as “open your database and manually add these columns.” Database design changes during development just as application code does. Migrations represented controlled schema evolution in project history, while seeders helped establish expected development or test data.

They did not eliminate every database conflict, and seeders were not a reason to commit production data. They gave the team a reproducible mechanism for expected structure and starting data.

06 / .env Was Also Part of Architecture

Portable Does Not Mean Hard-Coded

Students had to ask what belonged in code, what belonged in configuration, what needed to remain secret, and what changed between environments. The template's sample covers database hosts, ports, names, usernames, passwords, and a MongoDB connection URI without requiring real local values to be committed.

Repository

  • Application code
  • Configuration schema or sample
  • Docker definitions
  • Migration definitions
  • Seeder definitions

Local environment

  • Secrets
  • Local `.env`
  • Machine-specific values
  • Environment-specific overrides

The repository's `.gitignore` excludes `.env`, and `.dockerignore` excludes environment and development-secret files from the build context. Reproducibility required documenting configuration without publishing credentials.

07 / SQL First, NoSQL Second

Learn Both. Then Decide.

Relational concepts→Document-oriented concepts→Project constraints→Defensible choice

Relationships

Does relational integrity matter, and how do entities reference one another?

Shape

Is the data naturally document-shaped, and can its shape vary?

Access

What queries and update patterns does the application actually need?

Cost

What complexity does another storage model introduce?

Students first learned SQL, then NoSQL, and eventually had to choose what their system needed. PostgreSQL was not automatically superior, and MongoDB was not justified merely because it felt newer.

08 / The Common NoSQL Mistake

NoSQL Did Not Mean Dump Everything Into MongoDB

After learning NoSQL, some students tried to move too much data into it because it was the newer concept they had just encountered. Others made systems more complicated by adding multiple storage models without a real requirement.

They had to explain what data belonged there, why it belonged there, how the application would access it, what relationships it carried, and what maintaining another database would cost.

A database choice is still an architectural decision, even in a classroom project.

09 / Some Students Used Both

Then Some of Them Connected Two Data Models

Students could choose one storage approach, but some successfully assigned different responsibilities to PostgreSQL and MongoDB. They maintained relationships through IDs and used an adapter conceptually to coordinate calls and related references across the boundary.

Using two databases increased complexity. The work was notable because students had to manage that complexity deliberately, not because dual storage was the preferred answer for every project.

10 / The Overhead Was the First Lesson

At First, Setup Felt Like Extra Work

Students had to learn Docker, environment configuration, migrations, seeders, Composer dependencies, database services, ports, and repository workflow before application features felt immediate.

  1. First projectSetup feels expensive
  2. Repeated practiceCommands and structure become familiar
  3. Multiple projectsEnvironment setup becomes routine
  4. Different computerReproducibility starts paying for itself
  5. Group workThe team shares one base environment

Compared with opening a basic PHP project and coding immediately, the initial cost was real. Its value appeared through repeated use.

11 / Preparing for CI/CD and Capstone

Deployment Readiness Started Before Deployment

In another teaching context, these practices also prepared students for later capstone work. A deployable project needed more than source code: dependencies, configuration, database services, migrations, seeders, reproducible startup, secrets, and deployment configuration all required attention.

Repository→Reproducible build and environment→Configuration→Database migration→Application start→Validation→Deployment

The public template does not implement a complete production CI/CD pipeline. It helped make CI/CD concepts easier to introduce by requiring students to think about what another environment would need.

12 / Discipline Beyond the Codebase

The Code Was Only One Part of the Project

Once students understood that files had responsibilities, the next step was showing that application parts, databases, services, configuration, and environments had responsibilities too. This continued the reasoning described in Teaching Structure Before Frameworks without repeating its file-organization lesson.

Project disciplineCodeStructureConfigurationDatabaseEnvironmentVersioningCollaborationDeployment considerations

The application was not only its source files. Working CRUD and PHP syntax mattered, but so did separation of concerns, database design, migrations, seeding, reproducibility, collaboration, and technology selection.

13 / What Changed

They Could Change Machines and Keep Working

Observed outcomes, not measured KPIs

  • Fewer environment-specific problems
  • Easier switching between machines
  • More consistent team setups
  • Faster database recreation
  • Better database-change discipline
  • Better understanding of migrations
  • Better environment-configuration awareness
  • Less dependence on one student's machine
  • Stronger collaboration
  • Greater deployment awareness
  • More familiar reproducible setup
  • Faster starts after repeated practice
  • Better SQL and NoSQL tradeoff reasoning

I observed students moving between home machines and school computers without needing the original machine where a project began. This sometimes surprised students from other classes who were accustomed to projects being closely tied to one local setup. That comparison is a classroom observation, not measured institutional evidence.

14 / Closing

The Project Stopped Belonging to a Laptop

The result I valued was not memorized Docker commands. It was the ability to move to another suitable machine, reconstruct the environment, restore the expected database structure, configure the project, and continue developing with a team.

A predictably reconstructable project is closer to being deployable and maintainable than one whose environment exists only in someone's memory. Docker helped, but portability came from the combination of repository discipline, environment definition, configuration, migrations, seeders, dependency management, and shared workflow.

The project stopped belonging to a laptop and started belonging to the repository.

The extra setup became worthwhile because students could continue on almost any suitable machine that supported the required Docker environment.
