Original 8-Hour Submission

The 8-Hour Challenge

SaanKain began during an online development event conducted through Meet and connected with Kimi as part of a Kimi promotional event. Participants received three randomly assigned topic options; I selected Food.

The goal was not to invent a startup or production SaaS. It was to deliver a working solo application inside the event window while using Kimi, following the provided instructions, and considering responsible handling of information.

TimeApproximately eight hours from ideation to submission.
TeamOne developer responsible for product decisions, implementation, and delivery.
TopicFood, selected from three randomly assigned options.

Constraints Defined the Product

DeadlinePrioritize working vertical slices over infrastructure completeness.
Required IntegrationsUse Kimi and the event-provided API in the core experience.
Accessible ResourcesWork within limited or free tools without a conventional production database.
Engineering DisciplineKeep the implementation readable, maintainable, responsive, and uncomplicated despite the deadline.
TestingFeature delivery took priority; comprehensive testing was deferred until after the event.

Original 8-Hour Submission

From Food Prompt to Nearby Restaurant

Natural language was chosen because it resembles how people decide what and where to eat. A person can say “cheap sushi near Makati,” “best ramen near me,” or “restaurants open now” instead of configuring a long sequence of filters.

User Prompt
    ↓
Kimi Interpretation
    ↓
Restaurant Intent + Location Context
    ↓
Event-Provided Restaurant API
    ↓
Relevant / Nearby / Best Results
    ↓
Save Useful Places on the Device

The event implementation used restaurant, location, distance, open-now context, and ratings where available for “best” style results. These are historical event behaviors; the current free-tier Foursquare transformation does not expose ratings.

Original Principle · Current Controls Verified Separately

GDPR-Informed Privacy by Design

Privacy and GDPR-related research consumed a meaningful part of the ideation window. The practical design question became: what information genuinely needs persistence, and what has a justified reason to leave the device?

Keep user data on the device unless a feature genuinely requires transmission or external storage.
USER DEVICE
├── Search History
├── Saved Restaurants
└── Location State

USER CONTROLS
├── Delete one
├── Clear all
└── Disable location

EXTERNAL SEARCH
└── Only required query/location context

The competition history does not conclusively verify IndexedDB, so the original implementation is described conservatively as on-device browser persistence. The current repository explicitly uses localStorage.

Current master · Source Verified

Bounded AI Search Architecture

Next.js UI / Pages
      ↓
Hooks / Page Logic → Search Service
      ↓
GET /api/v1/execute
      ↓
Access Code + Message + Coordinate Validation
      ↓
Natural-Language Parser
├── Groq JSON interpretation → Zod validation
└── Deterministic cuisine/location/open-now rules
      ↓
Foursquare Places → Transform → Rank → Structured Results

The LLM extracts bounded search fields; it does not directly own the result experience. Invalid or unavailable LLM output returns control to deterministic application rules. The server route validates message length and latitude/longitude ranges before parsing or place lookup.

Current Search and Ranking Behavior

ParsingGroq uses a low-temperature JSON response for cuisine, location text, and open-now intent; Zod validates the response shape.
FallbackRegex and keyword rules recognize supported cuisines, open-now wording, location after “near,” vague near-me language, and a small Tagalog-to-English mapping.
LocationKnown Metro Manila place text is normalized for Foursquare; enabled browser coordinates drive distance-sorted near-me searches.
RankingCurrent ranking scores cuisine/category and open-state matches, includes a rating boost only if rating data exists, and uses distance as a tie-breaker.

Current Location & Local Persistence

Location activates only through a user action. The hook requests browser geolocation, reverse-geocodes coordinates through OpenStreetMap Nominatim, persists location state locally, and removes stored coordinates and location details when disabled.

BookmarkslocalStorage, individual removal, clear all, maximum 20 entries.
Search HistorylocalStorage, deduplication, individual removal, clear all, maximum 50 entries.
PreferencesTheme, result view mode, sort field, and direction are browser-local.

Technical Decisions

Natural Language Before Filter Complexity

Decision: Let people describe what they want conversationally, then translate that intent into bounded search parameters.

Device-Local Utility Without Accounts

Decision: Keep history, favorites, and location state under user-controlled browser persistence for prototype scope.

AI Inside Deterministic Boundaries

Decision: Validate structured LLM output and retain deterministic parsing so search behavior does not depend entirely on an AI response.

Vertical Slices Under Deadline

Decision: Establish a real end-to-end restaurant result early, then add persistence, deletion controls, location, and refinement.

Constraints & Tradeoffs

Eight HoursComplete vertical slices instead of production infrastructure.
Solo DeliveryKeep architecture shallow enough to understand and change quickly.
Privacy QuestionsPrefer local persistence and explicit user controls.
AI RequirementUse AI for intent interpretation without making AI the entire application.
CostTransition post-event integrations toward accessible resources.

Retrospective

Solve the user problem first, then decide where AI meaningfully improves the solution.

During the event, a significant amount of attention went into how AI could be incorporated while understanding privacy and GDPR-related constraints. The more durable lesson was to ask what deeper user problem needed solving, what information was actually necessary, and what data had a justified reason to leave the device.

The event appeared to value innovation, broader idea potential, and more agentic AI usage. SaanKain made a different tradeoff: it optimized for a complete, privacy-conscious, usable prototype rather than maximizing agentic complexity. That distinction became an improvement in engineering judgment, not a regret about the result.
